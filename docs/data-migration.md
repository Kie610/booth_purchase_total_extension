# 保存データ・バックアップの移行とCSV出力

取得した注文・金額・商品明細・ギフト情報を保持し、対応する旧形式のJSONを最新版へ変換してから読み込む。移行・復元の経路はバックアップJSONだけで、CSVは出力専用。新しい形式を追加するときも、既存データを削除して再取得することを移行手段にしない。

## バージョンと変換

- アプリのデータ形式は `appVersion`、バックアップの外枠は `version`、注文を取得したときの情報量は `cache[id].v` で区別する。
- ファイル名は `booth-backup-1.2.0-20260907.json`、`booth-orders-1.2.0-20260907.csv`、`booth-items-1.2.0-20260907.csv` の順。絞り込みCSVは `orders-gift` など種類に対象を含める。
- 旧ファイル名にアプリ版がない1.0.0・1.1.0は、既知のJSON構造から互換形式を判定する。同じ形から元のアプリ版を断定しない。
- 今後はファイル名と内容のアプリ版を照合し、登録した隣接版の変換を順に適用する。変換経路がない版、未来版、版の矛盾、壊れたデータは保存前に拒否する。
- 変換は入力を直接書き換えず、各段階で情報を保持する。未取得のgiftId等を補ったふりをして、注文の収集版を上げない。

## 保存と併合

内部データの形式変更で既存値を書き換える場合は、移行前のデータを保存してから変換結果を確定する。版の記録と省略項目の追加だけなら、取得値を変更せず、そのまま残す。保存に失敗したときは元データを消さず、完了扱いにしない。再起動で未完了の原本を上書きしない。既にあるロックを使い、他タブの収集・復元との競合を避ける。

復元はロック取得後に最新の保存データを読み、検証・変換・併合・保存を済ませてから画面の状態へ反映する。終了処理で古いタブのキャッシュを無条件に保存しない。

注文IDは文字列で扱い、同じ注文を二重計上しない。既知の金額や明細を、不明・省略された値で置き換えない。金額や割り当ては既存の既知値、明細は完全な側を優先し、相違する両側の原形も残す。正当な複数の商品行と、同じファイルの再取り込みを区別する。同名明細の対応を確定できない場合は価格や数量を推測で補わない。

`cache[id].importedAlternatives` と注文索引の各行の同名フィールドには、主値と異なる元データを保管する。割り当て・受取状況の相違と、全件再取得で集計対象から外れた明細は `migrationConflicts` に保管する。これらは二重計上せず、JSONで持ち出せる。

内部キーは `boothDataVersion` が版、`boothDataMigration` が移行記録、`boothMigrationConflicts` が相違データ。`{before, after}` の保存→適用先の保存→同じ記録を `{before, complete:true}` へ縮小する順で確定する。原本を別キーへ重複保存しない。途中で失敗したら同じ未完了記録から再開する。初期移行・復元・通常収集は同じWeb Lockと期限付きロックを使う。

保存容量不足で移行が進まなくても、JSON出力は読み取りだけで利用できる。未完了の両側を変換・併合したバックアップを作り、保存処理やロック取得の書込みを要求しない。JSON出力は保存原本のスナップショットなので、別タブで収集中の場合は途中までの取得内容を含み得る。

## CSVの用途と限界

CSVは表計算ソフトでの集計、外部ツールへの取り込み、注文番号列を除いた共有のための出力であり、データの移行・復元には使わない(オーナー決定、2026-09-09)。列構成は1.0.0・1.1.0と同じで、絞り込み中の「集計対象」列以外の列・補助行を足さない(外部ツールが列位置や行数に依存して読む)。ファイル名のアプリ版は残す。文字列セルの数式開始文字はアポストロフィで保護し、負の金額は数値のまま出す。

1.2.0だけは末尾に `データバージョン` と `復元用データ` の列を付け、バックアップJSONを分割して埋め込んでいた。外部ツールでの取り込みが壊れ、共有向けの出力に受取状況・メモ・手動割り当てが混ざるため1.2.1で出力を廃止し、CSVの読み込み(1.0.0・1.1.0の表示列CSVと1.2.0の復元列付きCSV)も取りやめた。1.2.0のCSVしか手元にない利用者は、BOOTHから再収集する。`cache[id].csvFacts` は過去のCSV取込で保存された原行で、値を保つためだけに読み書きを残す。

## 形式を変えるときの必須確認

1. 旧版からの変換経路を追加し、新旧の版と欠落の意味を明記する。
2. 旧JSON・内部データを合成データで検証する。
3. JSONの書き出しと読み戻しで、注文、明細、金額、ギフトID・状態・メモ、手動割り当てが保たれることを確認する。CSVは表示列の内容を確認する。
4. 逆順での補完、同一ファイルの再取り込み、部分データ、既知値の衝突、保存失敗、再起動、別タブを検証する。
5. 保存済みデータを破棄する操作や再取得だけに頼る移行を実装しない。

版を進めるときは `manifest.json` と `DATA_VERSION` を揃え、`DATA_MIGRATIONS` へ直前の版から新しい版への関数を追加する。構造を変えない版でも、値を保つ変換を登録する。古い変換を消さず、入力を複製してから全段階を適用する。欠落を埋める変換は「存在しない項目」と「存在する不正値」を区別し、不正値を空の値へ置き換えて受理しない。

## 検証方法

- `node test/migration-check.cjs` — 旧版JSON、版の順次変換、併合、JSONの完全往復、CSV出力の列と文字列の境界。
- `test/index.html` をHTTP配信して幅768px以上で開く — 既存の画面・集計・収集テスト。
- `node test/migration-browser-check.cjs` — 実際のdashboardをChrome上で開き、合成ストレージで移行、保存失敗、再起動相当、2タブの競合、出力UIを検証。HTTP配信を先に起動する。既存のPlaywrightを `NODE_PATH` に指定し、必要なら `BOOTH_TEST_URL` で既定の `http://127.0.0.1:8732` を変える。外部通信は遮断する。

通常のキャッシュ削除は利用者による明示操作であり、形式移行とは区別する。復旧原本・相違データ・メモ・割り当ては通常のキャッシュ削除後も残る。実BOOTHでの収集・実拡張プロファイルの更新・Excel本体での再保存は、合成データの検証だけでは確認済みにしない。
