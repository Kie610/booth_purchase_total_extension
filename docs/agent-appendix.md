# エージェント補遺

`AGENTS.md` の補遺。委任、並行実装、リリース、引き継ぎ文書の整備のいずれかを行う前に読む。
毎回のセッションで必要な規則は `AGENTS.md` にあり、ここには特定の場面でしか使わない規則だけを置く。
判断理由、履歴、過去の文章は `docs/handoff-history.md` が持つ。

## 委任と検品

- 親セッションが計画・委任・検品・統合・コミットを担い、サブエージェントは委任範囲だけを実装する。
- 委任結果は差分・テスト件数・受け入れ条件を検品してから採用する。件数の無い合格報告は採用しない。
- サブエージェントは委任範囲外を変更せず、merge・push・deploy・publish・権限変更を行わない。
- 委任先モデルの階層は `subagent-delegation-tiers` スキルに従う。スキルが無い環境では、機械的な合否検証を
  反復できる作業を下位モデル、一発勝負の推論・帰納・設計判断を伴う作業を上位モデルへ割り当て、迷ったら上位へ寄せる。
- 委任1回あたり約45〜55kトークンの固定費がかかる。単発の小さな作業は親セッションが直接実行するほうが安い。
- 委任の利得は安いモデルへ移すことではなく、読み込んだ内容を親の文脈へ残さないことにある。親の文脈が200kトークンを
  超えたら、読み込みを伴う作業(複数ファイルの通読、ログ調査、大量出力の確認)は作業量にかかわらず委任を既定にし、結論だけを受け取る。

### 委任プロンプトへ必ず含める項目

1. 目的: 何を達成したら終わりかを1文で。
2. 対象範囲: 変更してよいパスと、変更してはいけないパス。
3. 実行する検証コマンド: そのまま実行できる形で。
4. 受け入れ条件: 件数、終了コード、出力文字列など観測可能な条件。集約させる数値は数え方の定義まで具体値で固定する。
5. 権限境界: コミット、push、外部書き込み、破壊操作の可否。
6. 報告形式: 返させる項目の列挙。
7. 停止条件: 判断できない場合に自走せず停止して報告させる条件。

### 検品で裏を取る項目

- `git status` と差分で、申告範囲外の変更が無いか。
- 「テストが通った」に実行コマンドと件数の記載があるか。件数の無い合格申告は採用しない。
- skipや未実行を合格へ含めていないか。
- 委任時の受け入れ条件を1つずつ満たしているか。
- 依頼していない整形・リネーム・リファクタリングが混ざっていないか。
- 「確認したこと」に対象・手順・観測結果がそろっているか。欠けた項目は未確認として扱う。
- 「確認済み」と主張された箇所と実際の差分が矛盾していないか。矛盾は最優先で確かめる。
- レビューを委任した場合、依存先のソースを読んだ裏取りがあるか。依存先を読めないレビューは多数決でも誤る。

不合格の場合は、階層を上げるか、条件を具体化して同じ階層へ差し戻す。合格するまで成功として報告しない。

## 並行実装のworktree運用

- 並行実装では各サブエージェントへ専用worktreeと専用ブランチを割り当て、同一checkoutを共有しない。
- 各サブエージェントは自分のworktree内でテストと検証を実行する。ポートはworktreeごとに分ける。
- 統合は親セッションが、サブエージェントのworktreeとは別の場所で差分を検品してから行い、統合後テストを実行する。
- 並列分割は固定費を分割数だけ支払う。1委任の作業量が固定費を大きく超える場合だけ分割する。

## バージョンブランチとリリース判定

- 現在の正式リリースは `1.1.0`。開発中の統合ブランチは `1.2.0-dev`。
- 正式リリースが確定するまでは、`main`へ直接コミット・マージ・pushしない。
- 正式リリース時は、検証済みバージョンブランチへ`main`をfast-forwardして同じコミットにそろえる。
- `main`の同期後は、ローカル・リモートの`main`とバージョンブランチが同じSHAであることを確認する。
- 開発中の統合ブランチ名は `<次版のversion>-dev`(例 `1.2.0-dev`)。リリース済みブランチ名は `manifest.json` のversionと
  完全に一致させる。`-dev` ブランチを作るときに `manifest.json` のversionを次版へ上げる。
- リリース時はユーザーへバージョン名を確認し、承認を得てから `<version>-dev` を `<version>` へリネームして固定し、
  同じコミットへ注釈付きタグ `v<version>` を打つ。リネーム後は同期した `main` から新しい `<次版>-dev` を切る。
- バージョンブランチは削除しない。次の版は正式リリース後に同期した`main`から作る。
- ある程度大きな機能追加ではマイナー番号を上げて `X.Y.0` とする。
- バグ修正や小さな機能変更ではパッチ番号を上げて `X.Y.Z` のZを更新する。
- 開発用ブランチは対象の `-dev` ブランチから分岐し、検証後に同じ `-dev` ブランチへ統合する。
- fast-forwardできない場合は履歴を書き換えたりforce pushしたりせず、作業を止めてユーザーへ確認する。
- 公開前に、コードのライセンス、素材の権利、クレジット、非公式である旨の記載、保存データとプライバシーの
  説明がそろっていることを確認する。ライセンスが未確定なら公開前のblockerとして扱う。
- 詳細な手順は `docs/versioning.md` にある。

## ディレクトリとバックアップ

- 過去版のコピー(`_old`、`_bak`、`v2/`、日付付きフォルダ)をリポジトリ内に作らない。過去版はバージョンブランチと `vX.Y.Z` タグが持つ。
- 秘密・個人設定・一時コピーは `.local/`(`.gitignore` 済み、バックアップ対象外)だけへ置く。
- 手順の正本は `docs/` に書く。`tools/` のスクリプトはそれを機械化したものであり、正本にしない。
- 再取得が難しい素材(著者近影など)は `CREDIT.md` に取得元とライセンスを書く。復元不能なものはその旨を明記する。
- 第一のバックアップは `origin` への push。変更があれば3日以内、リリース時と破壊的操作の前は必ず push する
  (push 自体は既存規則どおりユーザーの許可を得てから行う)。
- 加えて年1回と方式変更時に `git clone --mirror` を保存先 `D:\GitHub_WorkSpace\BrowserExtensionackup\` へ置く
  (ユーザー指定、2026-09-05。同一ドライブである点は承知のうえ)。mirror は3世代以上残し、
  古い世代は新しい世代の復元確認の後にだけ消す。
- 復元を試していないバックアップは未検証として扱う。年1回、別の場所へ復元して `tools/release.ps1` が通るまで確かめ、
  結果を `docs/handoff-history.md` へ日付付きで1行残す。実行していない検証は PASS ではない。
- reset、大規模な移動・改名、履歴の書き換えの前には、作業ブランチへコミットするか `backup/<日付>-<内容>` タグを打つ。
  stash に頼らない。タグは検証後に削除し、残す場合は理由を履歴へ書く。
- 実施記録は `docs/handoff-history.md` の時系列に書く。

## 引き継ぎ文書の保ち方

- ルートの `HANDOFF.md` は `HANDOFF.agent.md`・`AGENTS.md`・`docs/agent-appendix.md`・`docs/handoff-history.md`
  への短い索引に保つ。現在状態の全文や永続規則を複製しない。
- 置き換える詳細情報は、短縮前に `docs/handoff-history.md` へ保存する。原文をそのまま保存できなかった場合は、
  正規化の内容と理由を履歴へ記録する。
- `AGENTS.md` は100行・8192bytes以内、`HANDOFF.agent.md` は原則4096bytes以内に保つ。byte数は改行をLFへ
  正規化してから数える。
- 上限に近づいたら、設計思想の節と規則を削らず、詳細な理由・背景・経緯を `docs/handoff-history.md` へ移す。
- `HANDOFF.agent.md` は Agent handoff v1 schema の見出し・key・順番を変えずに使う。分からない値は `unknown`、
  存在しない値は `none`、未実行の検証は `not-run` とし、値を捏造しない。
- 事実を書く箇条書きは `C`(確認済み)・`A`(未検証の仮定)・`U`(未解決、安定ID付き)のいずれかで始める。
  証拠なしに `A` や `U` を `C` へ昇格させない。
- `verified:` の各行は `status; kind; command; environment; scope; counts` の順で書く。PASSはpassedが1件以上かつ
  failed・skipped・not-runがすべて0の場合だけ。skipと未実行は `not-run` へ記録する。
- `Next` の各項目は `blocked-by: none` または `blocked-by: U<n>` で終わらせる。リスクや好みをブロッカーにしない。
- 運用ルール合成の手順パッケージを適用したときは、`docs/handoff-history.md` の `## Migration record` にある `procedure:` へ
  版・貼ったファイル名・適用日を1行追加する。既存の行は消さない。
