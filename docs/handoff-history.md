# 引き継ぎ資料

新しいセッションで「BOOTHお買いものレポート」拡張機能の開発を続けるための資料です。
最初に作業場所とGit運用、その後にプロジェクト構造、検証方法、調査済みの技術知見を記載します。

新しいチャットは、割り当てたworktreeをソースフォルダとして開き、次の一文から始められます。

> このworktreeの HANDOFF.md を読み、現在のブランチと変更状態を確認してから、
> BOOTHお買いものレポート拡張機能の作業を引き継いでください。

## 1. 作業環境と役割

- リポジトリ: https://github.com/Kie610/booth_purchase_total_extension
- 応答、コミットメッセージ、ユーザー向け文面は日本語にする
- CodexとClaude Codeは、同じGitリポジトリに接続された専用worktreeで開発する
- フォルダの実パスは固定しない。チャットを作るときに、対応するソースフォルダを指定する

### バージョンブランチ方針

- 正式リリースは`1.0.0`。現在の統合・配布ブランチも`1.0.0`とする
- ユーザーが明示的に方針を変更するまで、`main`へcommit・merge・pushしない
- 統合先にはmanifestのversionと完全に同じ名前のブランチ（例: `1.0.0`、`1.1.0`、`1.0.1`）を使う
- バージョンブランチはリリース後も削除せず、履歴として残す
- ある程度大きな機能追加ではマイナー番号を上げて`X.Y.0`とする（例: `1.0.0` → `1.1.0`）
- バグ修正や小さな機能変更ではパッチ番号を上げる（例: `1.0.0` → `1.0.1`）
- 次のバージョンブランチは、直前のバージョンブランチの検証済み先端から作る

### チャットとソースフォルダの対応

| エージェント | チャット | 指定するソースフォルダ | 使用ブランチ | 役割 |
|---|---|---|---|---|
| Codex | 開発用 | Codex用worktree | `codex/<task>` | 実装、担当テスト、commit |
| Claude Code | 開発用 | Claude用worktree | `claude/<task>` | 実装、担当テスト、commit |
| Codex | マージ用 | 統合用worktree | `<version>` | ブランチ統合、全体テスト、push |
| Claude Code | マージ用 | 統合用worktree | `<version>` | ブランチ統合、全体テスト、push |

CodexとClaude Codeのマージ用チャットは同じ統合用worktreeを参照します。
**マージ用チャットは、トークンやコンテキストに余裕がある側を1つだけ選んで動かし、同時に操作しないでください。**
開発用チャットには担当worktreeだけ、マージ用チャットには統合用worktreeだけを指定します。

### 役割の厳守

開発用チャットとマージ用チャットは役割を兼任しません。依頼内容が現在のチャットの役割と
一致しない場合は作業を始めず、「別の担当チャットへ送るプロンプトを誤って送信した可能性がある」
と伝え、正しい担当へ依頼し直すよう案内します。

- **開発用チャット**は、機能実装、修正、担当範囲のテスト、**`README.md`と`HANDOFF.md`の
  文書変更**、開発ブランチへのcommitを担当する。
  バージョンブランチへのmerge、統合後の全体確認、pushを依頼された場合は断り、マージ用チャットへ案内する
- **マージ用チャット**は、受け取った開発ブランチのmerge、機械的な競合解消、統合後の全体テスト、
  ユーザー許可後のバージョンブランチのpushだけを担当する。新機能の実装、仕様変更、不具合修正、通常の文書変更を
  依頼された場合は断り、開発用チャットへ案内する
- マージ中に仕様判断や実装修正が必要になった場合、マージ用チャットで作り込まず、開発担当または
  ユーザーへ戻す。役割外の依頼を「小さな変更だから」という理由で引き受けない

**文書変更を開発担当に寄せているのは、手が空いているかどうかではなく次の3点のためです。**

- 統合用worktreeは2つのマージ用チャットで共有される。文書作業で未コミット変更を抱えると、
  もう一方がmergeを始められない。開発担当は専用worktreeを持つのでこれが起きない
- 文書commitのたびに統合先のバージョンブランチが動き、実装中の開発ブランチが古くなる確率が上がる。
  開発担当が作れば統合先が動くのはマージ時だけになる
- 統合先への直接commitは誰も差分を読まない。開発ブランチにすれば、
  マージ担当が差分を読む通常の経路に乗る

### worktree共通ルール

- 同じworktreeを2つのエージェントから同時に編集しない
- 開発用チャットはバージョンブランチへ直接実装しない
- 全チャットは、ユーザーが明示的に方針を変えるまで`main`へcommit・merge・pushしない
- マージ用チャットは統合に専念し、新機能を追加しない
- 他方のworktreeへ直接ファイルを書き込まない。変更はcommitとmergeで受け渡す
- 作業ツリー、ブランチ、未コミット変更はworktreeごとに独立する。Gitオブジェクトとリモート追跡情報は共有される
- worktreeの追加・削除はフォルダ操作ではなく`git worktree add` / `git worktree remove`で行う

## 2. 標準開発フロー

### 2.1 開発用チャット

開始時に担当worktree、ブランチ、未コミット変更を確認し、リモートの最新情報を取得します。

```bash
git status
git branch --show-current
git worktree list
git fetch origin
```

必要なら`git rebase origin/<version>`で最新のバージョンブランチへ追従します。共有済み履歴なら`git merge origin/<version>`を使います。
未コミット変更がある状態では、変更の所有者と目的を確認するまでrebaseやmergeをしません。

**実装は必ず最新の`origin/<version>`を分岐元にします。** 依頼文に書かれたバージョンブランチの位置は、
書かれた時点のものです。もう一方のマージ用チャットがpushしていると既に古くなっているため、
依頼文を信用せず`git fetch origin`で確かめてから分岐します。

```bash
git fetch origin
git log --oneline -1 origin/<version>
```

分岐元が古いまま実装すると、統合時に競合します。競合の解消はマージ用チャットの役割ではなく、
実画面での確認ができる開発用チャットへ差し戻されるため、作り直しになります。

**作業手順そのものの文書は、機能実装とは別のブランチにします。** 何をどちらへ載せるかは、
「その変更は、機能が入らなかったときに取り込んでよいか」で決めます。

| 対象 | ブランチ | 理由 |
|---|---|---|
| その機能を説明する文書（`README.md`の機能説明、HANDOFF 3〜6章） | 機能と同じ | 機能が入らないのに説明だけ入ると内容が嘘になる |
| 作業手順そのものの文書（HANDOFF 1〜2章） | 別ブランチ | 機能の成否と無関係に取り込めるようにする |

手順の文書を機能と同じブランチに載せると、**機能が差し戻されたときに手順の改善まで止まります。**
手順の改善は次のタスクの進め方に効くものなので、止めると同じ失敗を繰り返します。
ブランチ名は`codex/workflow-doc-...` / `claude/workflow-doc-...`のように、
機能ブランチと区別が付く名前にします。

これは4章の「関係のない変更を同じcommitへ混ぜない」とは別の話です。あちらはcommitの粒度、
ここではブランチの分け方を決めています。

1. 担当機能を実装する
2. 必要なテストを追加して実行する
3. 担当変更だけをcommitする
4. マージ担当へ、ブランチ名、コミット、変更概要、テスト結果、注意点を渡す

```text
ブランチ: codex/example または claude/example
先端: <そのブランチの先端の commit hash>
分岐元: <分岐元にした origin/<version> の commit hash>
概要: <変更を1行で>
テスト: <結果を1行で>
注意点: なし
```

**書くのは先端のcommitだけで足ります。** マージ担当は`git log <version>..<branch>`で中身を
確認するので、全commitを並べる必要はありません。

渡すブランチが複数ある場合は、`ブランチ`と`先端`を1行にまとめて並べ、他の項目は
そのまま1行ずつにします。取り込む順序があるなら、その順に並べます。

```text
ブランチ: claude/example-a (先端 <hash>), claude/example-b (先端 <hash>)
分岐元: <分岐元にした origin/<version> の commit hash>
概要: <変更を1行で>
テスト: <結果を1行で>
注意点: なし
```

報告を書く直前にもう一度`git fetch origin`を実行し、`origin/<version>`が分岐元のままか確かめます。
先に進んでいた場合は、報告せずに`git merge origin/<version>`で追従し、テストを通し直してから報告します。

**手順4の報告は省略しません。** commitが完了したら、ユーザーから改めて求められるのを待たず、
上記の項目をそのままマージ用チャットへ渡せるテキストとして提示します。このテキストは
マージ対象を特定するための短いバトンです。変更の詳しい説明、変更ファイル一覧、実装の背景は
繰り返さず、各項目を1行で書きます。詳細はマージ担当がcommitのログと差分を確認します。
注意点が無ければ必ず「なし」とだけ書きます。

未コミット変更は統合用worktreeからmergeできないため、開発用チャットはcommitまで完了させます。
作業ブランチのpushは、バックアップやレビューなど目的がある場合だけ行います。

### 2.2 マージ用チャット

マージ用チャットは統合作業専用です。開発ブランチとcommitの引き継ぎ情報が無い状態で
実装や修正を求められた場合は、開発担当へのプロンプトを誤って送信した可能性を伝えて断ります。

もう一方のマージ用チャットが動いていないことを確認し、統合用worktreeを最新化します。

```bash
git status
git branch --show-current
git worktree list
git fetch origin
git pull --ff-only
git merge codex/<task>
git merge claude/<task>
```

- バージョンブランチがクリーンであることを確認し、受け取ったブランチを1本ずつmergeする
- 受け取った「分岐元」が現在の`origin/<version>`と違う場合、mergeする前にその事実を伝える。
  競合するなら解消せず開発担当へ戻す
- 各merge後に差分を確認し、統合後に全テストを実行する
- 同じファイルの競合でも、意図が明確な機械的競合だけを解消する
- 仕様判断、片方の変更の破棄、テスト期待値の不一致が必要なら、開発担当またはユーザーへ確認する
- 大きな修正は統合用worktreeで続けず、原則として担当worktreeへ戻す
- 全体テスト後に`git status`と履歴を確認し、ユーザーの許可を得てからpushする
- pushは原則として統合用worktreeから一度だけ行う

```bash
git push origin <version>
```

**差分の確認には三点`...`を使います。** バージョンブランチが先に進んでいると、二点`..`は
「枝が消した変更」と「バージョンブランチにしか無い変更」を区別できず、追加しかしていない枝が
大量の削除をしたように見えます。枝が実際に変えた内容は分岐点との比較で見ます。

```bash
git log --oneline <version>..<branch>          # 取り込む対象
git log --oneline <branch>..<version>          # 枝が知らない統合先の変更
git diff --stat <version>...<branch>           # 枝が実際に変えた内容(三点)
```

**pushしたら、その時点の`origin/<version>`を開発担当へ伝えます。** 開発用チャットは自分の
worktreeしか見ていないため、統合先が進んだことに気付けません。次の実装が古い分岐元から
始まるのを防ぎます。

```text
push しました。現在の origin/<version> は <commit hash> です。
次の実装は git fetch origin で確認してから、この位置を分岐元にしてください。
```

### 2.3 並行開発

別worktree・別ブランチなら同時実装できます。開始前に担当範囲を分け、共通データ構造や
関数シグネチャを変える場合は相手へ伝えます。同じファイルを触る場合は、先に土台を統合するか担当順を決めます。

画面を増やす変更は、担当範囲を分けていても必ず同じ場所で競合します。`dashboard.html`のナビと
view区画、`dashboard-view.js`の`VIEW_NAMES` / `VIEW_TITLES` / `render()`、`test/index.html`の
骨組み、`manifest.json`のversionは、画面ごとに1行ずつ足す作りだからです。
**画面の追加を並行させないか、後から実装する側が先に統合を待ちます。**

## 3. プロジェクト概要

BOOTH (`accounts.booth.pm/orders`) の購入履歴から、実際に支払った合計金額を
**注文単位**で集計するManifest V3のブラウザ拡張です。

購入履歴一覧では、1注文で同じショップの商品を複数買うと、その注文が商品数だけ表示されます。
そのまま合計すると支払金額が多重加算されるため、**一覧を注文IDで重複除去してから、
注文詳細の「お支払金額」を1注文につき1回だけ取得する**設計です。この重複除去が拡張の核心です。

主に想定している利用者はVRChatユーザーです（購入点数が多く、作者への支援意識が強く、
購入額を共有する文化がある）。機能の取捨や画面の言葉づかいはこの層を基準に決めています。

### ファイル構成

```text
extension/
  manifest.json          MV3。権限は storage と https://accounts.booth.pm/* のみ
  icons/                 16/32/48/128。tools/make_icons.py が原本
  common.js              定数・日付解析・月/年集計・支出推移・商品明細の合計・索引の判定・ストレージ操作
                         (純粋な判定は上位から参照されるのでここに置く)
  purchase-examples.js   X共有用の金額比較マスター
  csv.js                 CSVへの変換のみ(DOMもストレージも触らない純関数)
  backup.js              バックアップの組み立て・検証・併合(同上)
  share.js               𝕏の共有文面と共有カードの描画(canvasへ描くだけ。stateは持たない)
  popup.html/css/js      収集済み合計の概要表示と集計ページへの導線
  dashboard.html/css     集計ページ(ハンバーガーメニューで画面を切り替える)
  dashboard-parse.js     BOOTHのHTML解析。構造変更時は主にここを修正
  dashboard-view.js      共通DOM参照とレポート画面の描画。イベントは扱わない
  dashboard-author-view.js 作者情報ダイアログの表示とフォーカス管理
  dashboard-insights-view.js ランキング・まとめ・支出推移の描画
  dashboard-share-view.js 共有ボタンと共有カード作成ダイアログの描画
  dashboard.js           状態、イベント配線、BOOTHからの取得
tools/make_icons.py      アイコン生成(Pillow使用)
tools/release.ps1        配布用ZIPとSHA-256チェックサムの作成
test/                    ブラウザ上で動くテスト
```

`dashboard-parse.js`、`dashboard-*-view.js`、`dashboard.js`はclassic scriptとして同じグローバルを共有します。
import/exportは使わず、`dashboard.html`のscriptタグ順が依存順です。表示層は共通・作者情報・分析画面・共有画面に
分割してあります。責務は「parse=入力、view=出力、dashboard=制御」で、viewからstateや`targetOrders()`を
読むのは想定内です。表示機能を追加するときは、対応する`dashboard-*-view.js`へ置きます。

ポップアップは閉じるとJavaScriptコンテキストごと破棄されるため、処理は専用タブへ移してあります。
Service Worker常駐はChromeでDOMParserが使えず、offscreen APIとFirefox対応の分岐が必要になるため採用していません。

### ストレージキー

- `boothOrderCache` — `{ [orderId]: { v, amount, gift, shipping, status, date, items } }`
  `items` は `[{ shop, shopUrl, name, price, quantity, boost, gift }]`。読めなかった場合は `null`。
  `v` は保存した項目の版数（`CACHE_SCHEMA_VERSION`）
- `boothOrderIndex` — `{ updatedAt, orders: [{id, status, date}], complete }`
- `boothSummary` — ポップアップ表示用の要約
- `boothRunState` — 実行中の進捗
- `boothDashboardTab` — 集計ページのタブID。tabs権限を使わず再フォーカスするために使う

### 画面と処理

画面はハンバーガーメニューで切り替えます。

| ハッシュ | 画面 | 内容 |
|---|---|---|
| `#/report` | お買いものレポート | 収集の実行と、合計・年別月別・注文ごとの内訳 |
| `#/ranking` | 推し作者ランキング | ショップ別の金額・購入数の上位 |
| `#/trends` | 支出推移・前年比較 | 2年の比較、月別・累計グラフ、曜日×時間帯 |
| `#/summary` | 今年のまとめ | 選んだ1年の支払額・点数・支援した作者数など |
| `#/export` | データ出力 | 注文単位・商品単位のCSV |
| `#/backup` | データの引っ越し | JSONの書き出しと読み込み |

レポート画面は、固定ヘッダー、収集済み合計、一括集計、折りたたみの「個別に収集する」、
年別月別集計、注文ごとの内訳、キャッシュ削除の順です。「個別に収集する」の中に
注文履歴の取得と月範囲を指定した金額収集を置き、初期画面では一括集計を主操作として見せます。
注文ごとの内訳は検索・ステータス絞り込み・日付／金額／ショップ順の並べ替えに対応します。
別画面の支出推移・前年比較では、今年と前年の
同期間比較、月別の棒グラフ、年間累計グラフ、共通の年別月別集計表を表示します。
固定フッターには合計、今年の金額、ギフト、件数、
黒地に白文字の「𝕏で共有」ボタンを表示し、実行中は進捗バーと中断ボタンを表示します。
フッター高は`--footer-height`と`body.has-progress`で切り替え、本文の下余白も追従させます。

処理は2段階です。

1. 一覧を新しい順に巡回し、注文IDで重複除去した索引を作る。金額はまだ取らず、既知注文に接続したら停止する
2. 年でまとめた表から月範囲を指定し、未収集の注文詳細ページから金額を取得する

## 4. 検証・commit・リリース

### テスト

**コード変更時は必ずテストを実行します。** Node.jsは無いため、Python 3.11で配信します。

**worktreeごとにポートを分けます。** 同じポートを使い回すと、別のworktreeのファイルを
読んだまま`ALL PASS`が出ます(下記「テストが嘘をつく条件」)。

| worktree | ポート | 開くURL |
|---|---|---|
| 統合用 | 8731 | `http://localhost:8731/test/index.html` |
| Codex用 | 8732 | `http://localhost:8732/test/index.html` |
| Claude用 | 8733 | `http://localhost:8733/test/index.html` |

```bash
python -m http.server 8733   # 自分のworktreeに割り当てられたポート
```

各worktreeのルートで起動し、割り当てられたポートの`/test/index.html`を開きます。
最終行が`ALL PASS`であることを確認してください。詳細は`test/README.md`にあります。

#### テストページにインラインスクリプトを書かない

`test/index.html` は拡張と同じ `script-src 'self'` を宣言しているため、
**インラインの `<script>` は実行されずに黙って捨てられます。** エラーも出ません。
エラー拾い(`test/harness.js`)と読み込み確認(`test/loaded.js`)を外部ファイルに
置いてあるのはこのためで、インラインへ戻さないでください。

かつてエラー拾いがインラインにあったため、読み込み時の構文エラーを誰も拾えず、
結果が「running...」のまま止まって原因が分かりませんでした。現在は
`loaded.js` が読み込めていないファイルを名指しします(cases.js が
スクリプトの一覧と付き合わせているので、ファイルを増やしたら
`REQUIRED_GLOBALS` にも足す)。

#### テストが嘘をつく条件

**`ALL PASS`だけで判断せず、必ずcheck件数まで見ます。** 件数が前回より減っていたら、
追加したテストが読み込まれていない、つまり別のファイルを見ている疑いがあります。
実際に、新規追加した22件が一度も実行されないまま`ALL PASS (357 checks)`と表示され、
FAILゼロで通ってしまったことがあります(正しくは379件)。

原因は、別のworktreeから起動した`python -m http.server`が同じポートに残っていたことです。
**Windowsでは、後から同じポートで起動してもエラーになりません。** Pythonの`http.server`が
`SO_REUSEADDR`を設定するため、2つ目のプロセスもそのままLISTENINGに入り、
同じポートに2つの待ち受けが並びます(実測確認済み)。どちらが応答するかは決まらないので、
古いworktreeのファイルが返ります。**起動時のエラー出力を見る対処は、そもそもエラーが
出ないので効きません。**ポートを分ける以外に確実な方法がありません。

疑わしいときは、そのポートに待ち受けが2つ以上無いかを見ます。

```bash
netstat -ano | grep ':8733' | grep LISTENING   # 2行以上あれば別プロセスが残っている
```

- 報告テンプレートの`テスト`欄には、`ALL PASS`と一緒にcheck件数も書く
- **受け取る側は、その件数を自分で実行した結果と突き合わせる。** 減っていれば、
  マージ後の全体テストが古いファイルを見ている
- 用が済んだテストサーバーは止める。止め忘れが次のworktreeの結果を狂わせる
- 機能を追加・変更したらテストも追加する
- 拡張APIは`test/stub.js`でスタブし、`extension/`の実ファイルを読み込んで検証している
- ブラウザペインのスクリーンショットは失敗しやすいため、必要に応じてDOMの位置、サイズ、
  計算後スタイルを実測して確認する
- BOOTHへのログイン済みfetch、ページング、実ページのセレクタは開発環境だけでは検証できない。
  必要な場合はユーザーへ実行を依頼し、結果を確認する
- 原因は推測で断定せず、ログ、イベント、レスポンスヘッダ、DOMなどを実測する

### commitとpush

- コミットメッセージは日本語で、何をしたかだけでなく、必要に応じてなぜ変更したかも記載する
- エージェント固有の`Co-Authored-By`などのトレーラーは、ユーザーが明示した場合だけ追加する
- 関係のない変更を同じcommitへ混ぜない
- pushは毎回ユーザーへ確認し、許可なく行わない
- push時は認証情報の都合で`$env:GIT_TERMINAL_PROMPT = "1"`が必要

### バージョンと配布物

- 正式リリースは`1.0.0`。`manifest.json`、README、テスト、配布物のversionを一致させる
- 統合先はversionと同名の永続ブランチにし、`main`へcommit・merge・pushしない
- ある程度大きな機能追加ではマイナー番号を上げて`X.Y.0`、バグ修正や小さな機能変更ではパッチ番号を上げる
- バージョンブランチは削除せず残す。方針変更はユーザーの明示がある場合だけ行う
- アイコンの原本は`tools/make_icons.py`。生成済みPNGを直接編集しない
- 配布物はPowerShellで`.\tools\release.ps1`を実行して作る。`dist/`にZIPとSHA-256チェックサムが出る
- ZIPのルートに拡張機能名フォルダが1つあり、その直下に`extension/`、`LICENSE`、
  `CREDIT.md`、`PRIVACY.md`があることを確認する。manifestは`extension/manifest.json`に置く
- `release.ps1`は一時フォルダに`<拡張機能名>-v<version>/`を作り、その中へ上記をコピーして
  ZIP化する。圧縮後は一時フォルダを`finally`で削除し、ZIPとSHA-256だけを`dist/`へ残す
- 同じversionの成果物を作り直す場合だけ`-Force`を付ける。通常は既存成果物を上書きしない
- Chromeウェブストアには公開しない。Firefoxは開発時の一時読み込みのみ確認済みで、署名・恒久利用は未対応

## 5. 守るべき設計

### 商品明細と画面の切り替え

- 合計・年別月別・注文ごとの内訳は、注文単位の**お支払金額**から出す。商品単価の合計で
  代用しない。**送料のある注文では実際に一致しないことを実測で確認済み**
  (お支払金額¥4,060 = 商品¥890×4 + 送料¥500)。置き換えると静かに合計がずれる。
  お支払金額から商品合計と送料を引いた残りを `amountGapOf` で出し、CSVの「差額」列と
  データ出力画面の件数表示で見えるようにしてある。クーポンやポイントなど、
  まだ拾えていないものがあればそこに出る
- **注文詳細ページには2つの型がある。ダウンロード商品と配送商品の両方で確かめること**
  - ダウンロード商品: `.sheet-group` の先頭に `b.u-tpg-title3` の見出し
    (「ダウンロード商品」「ギフト」)が入る
  - 配送商品: **その見出しが無い**。代わりに「〇〇から配送」の見出しと発送状況の
    バッジが入り、数量の行と送料の行が付く。
    かつて見出しの有無で商品のまとまりを判定しており、配送商品の注文がまるごと
    「明細なし」→未収集になっていた。**判定は商品リンク(`a.nav[href*="/items/"]`)の
    有無で行うこと。**領収書の枠も同じclassを使い回しているが、同じ判定で除外できる
- 金額の行のラベルは値の前に置かれる(`数量4` `BOOST¥ 0` `送料¥ 500`)。
  ラベルで種類を判定し、**見出しの付いた未知の行は読み飛ばす**。BOOSTと決めつけて
  足すと金額を取り違える(取りこぼした分は差額に出るので黙って消えることはない)
- 商品の金額は「単価×数量」にBOOSTを足したもの。数量の行はデジタル商品には無いので
  無ければ1個として数える。**BOOSTに数量を掛けていないが、数量2以上でBOOSTのある
  注文はまだ実測できていない**(掛け方を誤っていれば差額に出る)
- ギフト額は商品明細から算出する(`giftTotalOfItems`)。ギフトのグループに並ぶ商品の
  合計で、以前の `parseGiftTotal` と同じ値になる
- 商品の価格や数量を1件でも読めなければ、合計は0や1で埋めず `null`(不明)にする。
  足りない分を埋めると、少ない額を正しい合計として見せてしまう
- ショップ名は `.sheet-group` ではなく、外側の `.l-order-detail-by-shop` に1つだけ入る。
  同じショップのダウンロード商品とギフトは別グループだが同じ区切りの中に並ぶため、
  ショップの特定は必ず外側から行う。表示名は変わりうるので `shopUrl` も持つ
- **キャッシュのエントリには「何を保存したか」の版数 `v` を持たせ、現行版より古いものは
  `needsCollect` の対象にする**(`CACHE_SCHEMA_VERSION` / `isOutdatedEntry`)。
  保存済みのデータを見て欠落を推測する方式は採らない。日付から索引の抜けを検知しないのと
  同じ理由だが、この件では推測が原理的に不可能でもある。v0.15.0が保存した
  「ダウンロード商品だけの正しい注文」と「配送商品が欠けた混在注文」は、どちらも
  `quantity` と `shipping` を持たず、保存された形がまったく同じで区別できない。
  「差額が0でなければ疑う」も、クーポン利用の注文と見分けられないので使えない
  - 版数は**注文ごと**に持つ。ストレージ全体に1つだと途中まで取り直した状態を表せず、
    中断のたびに全件やり直しになる
  - **上げてよいのは、注文詳細ページから保存する項目が増えたときだけ。**
    表示や集計の変更で上げると、無関係な再取得を全ユーザーに強いることになる
  - 比較は `<` で行う。バックアップの復元でこの環境より新しい版のデータが
    入ってくることがあり、`!==` だと将来版まで取り直してしまう
  - 版を上げたら、なぜ再取得が走るのかを画面に出す(`outdatedArea`)。
    何も操作していないのに未収集が増えたように見えると、不具合と区別が付かない
- 商品明細を読めなかった注文は `needsCollect` の対象にし、次の実行で自動的に取り直す。
  内訳では金額の左に「明細なし」と出す(月別表では未収集として数えているので、
  内訳だけ収集済みに見せると食い違う)
- 画面はHTMLを分けず、同じページの中で区画を出し分ける
  (`#/report` `#/summary` `#/trends` `#/ranking` `#/export` `#/backup`)。
  別ページへ移るとJSのコンテキストごと破棄され、数分かかる収集が丸ごと止まるため。
  **画面を増やすときも別HTMLにしないこと**
- **レポート以外の画面では、未収集の注文があるか索引が未完了のときに、その旨と
  「お買いものレポートで収集する」リンクを必ず出す**(`renderPendingBanner`)。
  収集はレポート画面でしか行えないうえ、数字だけを見せて黙っていると、実際より
  少ない額を正しい合計だと思わせてしまう。案内は区画の外に1つだけ置いてあるので、
  **画面を追加すれば自動で付く。画面ごとに作り直さないこと**
- CSVはUTF-8のBOM付き・CRLF区切り(BOMが無いとExcelが日本語を文字化けさせる)。
  未収集や取得失敗は0ではなく空欄にする(0円の注文と区別が付かなくなるため)。
  明細の無い注文も商品単位のCSVに1行だけ残す(黙って落とすと買っていないように見える)
- 保存は `Blob` へのリンクを自前で作って押す。`downloads` 権限を足すと、
  権限は `storage` とBOOTHのドメインだけ、という現状が崩れる

### 画面の見た目をそろえる

画面を増やすたびに似たCSSが増えると、同じ意味のものが画面ごとに違って見える。
**新しい画面を作るときは、まず既存の共通クラスで組めないかを見ること。**

| クラス | 用途 |
|---|---|
| `.section-head` | 見出しと、その右に置く操作（年の選択、基準の切り替え） |
| `.stat-grid` / `.stat-card` | 数字を並べるカード。`statCard()`で作る |
| `.block-section` / `.block-head` / `.block-caption` | 画面の中の小見出しと説明 |
| `.empty-note` | データが無いときの案内 |
| `.segmented` / `.segmented-btn` | その場で切り替える選択（並べ替えの基準、画像の比率） |
| `.status` / `.status.warn` | 補足と注意 |

- **`.stat-grid`は`auto-fit`で列数を決める。** カードの数はBOOSTの有無や画面によって
  変わるので、列数を決め打ちすると空のマスや詰まった行が出る。
  折り返しは`auto-fit`が行うので、メディアクエリで列数を上書きしない
- 色は`:root`の変数から取る。`--border`は区切り線、`--border-strong`は押せるものの枠、
  `--bg-hover`はホバー。同じ色を各所に直接書かない
- 白地のボタンは`button.secondary`。`input[type=file]`だけは見た目を揃えられないので
  `label.file-btn`をボタンに見せ、寸法を`button.small`に合わせてある
- ランキングとまとめのショップ行は`renderShopRows`で共通にする。
  片方だけ列や飾りが違うと、見比べたときに別のものを数えているように見える
- 小さい文字やリンクをアクセント色の上へ直接置かず、白地用の`--accent-text`を使う。
  主ボタンと選択中の切り替えはアクセント背景に白文字を合わせ、`--accent`そのものはブランド色として維持する。
  手順番号の①・②は背景を付けず、アクセント色の文字だけで示す
- クリックできる表の行やセルはマウスだけにしない。実ボタン、または`tabindex="0"`と
  Enter／Space操作を用意し、開閉状態は`aria-expanded`で通知する。ショップへのリンクは別操作として残す
- モーダルは`role="dialog"`、`aria-modal="true"`、フォーカス移動・Tab循環・Escapeで閉じる操作・
  呼び出し元へのフォーカス復帰を一式で実装する。開いている間は背後を`inert`にする
- ヘッダー右端にコピーライトを置き、ハンバーガーメニューの最後に作者情報を開く項目を置く。
  作者情報は画面切り替えではなくモーダルで表示し、著者近影は`icons/author-kie.png`を同梱する
- 通常通知と進捗は`role="status"`、エラーは`role="alert"`を使う。実行中は`main[aria-busy="true"]`、
  進捗バーには`aria-valuenow`を設定する。見た目だけの更新にしない

### ショップ別の集計（推し作者ランキング・今年のまとめ）

- **ここだけは注文単位のお支払金額を使えない。** お支払金額は注文に1つしかなく、
  1つの注文が複数ショップにまたがるとショップへ割り振れないため、
  商品の合計（単価×数量＋BOOST）で集計する（`aggregateByShop`）
- そのため**送料やクーポンは入らず、ショップ別の合計をすべて足しても
  全体の合計支払額とは一致しない。画面に必ずその断りを出すこと**
  （配布する `dashboard.html` を読んで文面の存在をテストで検査している）
- 同じショップかどうかは表示名ではなく `shopUrl` で判断する
- 金額を読めなかった商品は0として足さず、件数を数えて画面に出す
- 王冠はMV3のリモートコード禁止に触れないよう、CSSの中にインラインSVGとして描く。
  外部の画像やフォントを読み込まないこと
- **数字の列は幅を決め打ちし、`table-layout: fixed` にする。** 基準を切り替えると
  太字になる行が入れ替わり、中身で決まる列幅がわずかに動いて数字が揺れる
- 順位をクリックすると、そのショップで買った商品を開く（`renderShopRows`）。
  同じ商品を複数の注文で買うと重複するので、`aggregateByShop` が名前で
  まとめたものを渡す。開閉の状態はランキングとまとめで共有する
  （別々にすると、行き来したときに開いたはずのものが閉じて見える）
- 並べ替えは `SHOP_SORTS` に名前で持ち、`aggregateByShop(results, sortBy)` に渡す。
  同額（同点数）のときはもう一方を第2の基準にし、それも同じなら名前順で固定する。
  ここを決めておかないと、再描画のたびに順位が入れ替わって見える
- **どちらで並べているかを画面に必ず出すこと。** 少額を多数買ったショップと高額を
  1点だけのショップでは1位が入れ替わるため、表の数字だけでは取り違える
- まとめの「はじめて買った作者」を出すため、**年で絞らず全期間の結果を渡す**
  （`buildYearSummary(results, year)`）。その年より前に買っているかを見ないと判定できない
- **その年より前の注文が未収集だと、明細が無いので前から買っていた作者を
  「はじめて」と数えてしまう。** 推測で補えないので `beforePending` に件数を返し、
  画面で断る。共通の未収集案内とは別に必要（あちらは金額が少ないことの案内で、
  こちらは数字が多すぎることの案内）
- **支払額が数値でも商品明細が無ければ、点数・作者数・推し作者は少なくなる。**
  `detailPendingCount` として金額未収集とは分け、画面と共有前確認の両方で断る
- 年のプルダウンには**注文のある年だけ**を並べる。1月に見ると去年を振り返りたいので、
  今年に注文が無ければ最も新しい年へ落とす
- BOOSTは0円でも金額の行自体は常にあるため、**0円を「応援した」と数えない。**
  ただし**BOOSTの項目自体を画面と共有文面から外してある**（使う人が少なく、
  「支援した作者」と語がぶつかるため）。集計は `buildYearSummary` に残してある

### 支出推移と曜日×時間帯

`common.js` の `buildSpendingTrend` が2つの年の月別値と累計を作り、画面側は描画だけを行う。
集計元は注文単位の「お支払金額」で、未収集や取得失敗は含めない。外部ライブラリは使わず、
月別比較はHTML、累計はSVGで描く。

- 比べる相手は既定で前年だが、第4引数で任意の年を渡せる。**同じ年を2つ渡すと比較対象が
  空になり差が全額になってしまうため、画面側で選んでいる年を相手の候補から外している**
- 対象月は、今年を選んだときだけ今月で切り、過ぎた年は12月まで見る
- 年別・月別表は `renderPeriodTableInto` をレポート画面と共用し、表ごとの開閉状態だけを分ける
- 曜日×時間帯は**注文件数**を色の濃さで出す（`buildWeekdayHourStats`）。
  **金額にしないこと。** 高額な1件でマスが真っ赤になると、その時間によく買うようには読めない
- 時刻は `parseOrderDate` が `hour` として拾う。無い表記もありうるので必須にしない
- **曜日は `Date.UTC` で数える。** ローカル時間で作ると環境によって1日ずれる
- 曜日か時刻を読めない注文は**0として置かず、除外した件数を画面に出す**。
  0時に寄せると、日曜0時にまとめ買いしたように見える
- **対象期間は年比較の左で選んだ年に合わせる**（`syncHeatmapToYear`）。同じ画面に
  違う期間のものを並べると、食い違ったものを見比べることになる
  - **期間はその年の1年間。今年でも今月で切らない。** ここで見るのは曜日と時間帯の
    傾向なので、月をそろえる意味がない。上の年比較が今月で切るのは、金額を足し合わせる
    以上、同じ月まででないと差が出てしまうからで、理由が違う
  - **上書きするのは年が変わったときだけ。** 毎回の再描画で合わせると、収集が進んで
    描き直されるたびに手で選んだ範囲が戻ってしまう（`heatmapSyncedYear`）
  - 範囲の選択肢には**注文のある月しか無い**ので、1月や12月を指定しても選べないことが
    ある。範囲に入る最も近い月へ寄せる（`clampMonthKey`）。寄せずに渡すと select の値が
    空になり、0件として表示される

### バックアップと復元

注文1000件の再収集には平均300ms間隔だけでも5分以上かかるため、収集済みデータをJSONで
書き出し、読み込み直せるようにしてある（`#/backup`）。CSV出力は人間が読む用途で、
復元にはJSONを使う。

- **復元は入れ替えではなく併合**（`mergeBackup`）。移行先が空なら結果は同じで、
  既にデータがある環境へ古いバックアップを読み込んだときに今あるものを失わない
- 同じ注文があれば収集済みの側を残す。今のものが未収集や明細なしのときだけ読み込んだ側で埋める
- 索引の `complete` は**両方が全期間のときだけ** true。片方でも途中までだと、
  つないだ結果に抜けが無いとは言い切れない
- 読み込んだJSONは `parseBackup` で対応バージョンと注文履歴・金額・商品明細の型を
  確かめてから使う。壊れたデータでストレージを上書きすると、収集し直す以外に戻す手段が無くなる
- CSVとバックアップには注文番号・商品名・ショップ名・購入金額が含まれるため、
  第三者へ共有しない注意を各画面で赤字・太字にして、保存操作の直前に表示する

### 索引、日付、キャッシュ

- 月キーは`2026-05`形式の0埋め。文字列比較と範囲判定がこの形式に依存する
- 注文日時の表記ゆれ（`2024年5月3日`、`2024/05/03`、`2024-05-03`）を数値化して比較する
- 索引の`complete`は、最古まで到達したか、既知注文に接続でき、以前の索引も完全な場合だけtrueにする
- 既知注文で打ち切ってよいのは、以前の索引が`complete`のときだけ（`stopAtKnown`）。
  未完了なら既知注文を読み飛ばして最終ページまで進み、古い側の抜けを埋めて`complete`にする。
  日付から抜けを推測せず、未完了時は全ページを辿る
- フラグを持たないv1.2以前の索引は完了扱い。当時は全ページ巡回成功時だけ保存していたため
- 全件再取得は最後まで完了した場合だけ古い索引を置き換える。途中終了時は取得済み分を併合する
- 全件再取得を最後まで完了した場合だけ、キャンセル済み・履歴外の注文の金額キャッシュも消す。
  増分取得では既知注文の状態を読み直さず、処理時間短縮を優先する
- 中断や失敗でも取得済みの索引は保存し、未完了として記録する
- 全件再取得でも収集済み金額キャッシュを先に消さない。`pendingTargets`がforce指定で全件を返し、
  取得できたものから上書きする。先に消すと索引取得中の中断で既存金額まで失われる
- 一覧を読めていない疑いがある場合は`complete`にしない。この判定は1ページ目だけでなく
  後続ページにも行う。注文が0件でもBOOTH公式の「購入履歴はありません」表示を読めた場合だけ
  正常な空履歴として完了扱いにする。注文も公式空表示も無い場合や、ページ送り枠があるのに
  ページ番号を1つも読めない場合は読み取り失敗として扱う
- 金額は5件ごとに保存し、中断やタブ終了後も続きから再開できるようにする

### ステータス、失敗、進捗

- ステータスは一覧ページを正とし、注文詳細ページからは読まない
- バッジclassは`STATUS_LABELS`の既知名を優先する。未知classは隠さず画面へ出す
- `boothRunState`には書き込み時刻とロック所有者を入れ、30秒以上更新のない進捗は無視する
- 一時的な通信エラーは最大2回再試行し、それでも失敗した注文だけ飛ばして全体処理を続ける
- 飛ばした注文はキャッシュへ書かず未収集のまま残し、次回実行で自動的に拾い直す
- 中断、ログイン切れ、HTTP 401・403（`isFatalFetchError`）は続行しても意味がないため、そのまま投げる
- リクエスト間隔は250〜350msのランダム値。再試行は2秒、4秒の指数バックオフとし、
  429では`Retry-After`を優先する。対象は408、429、5xx、ネットワークエラーだけで、
  401・403・404など恒久的な4xxは再試行しない
- 収集予定件数には平均300ms間隔を下限にした所要時間の目安を併記する。実際は通信時間が加わるため、
  「約N秒以上」「約N分以上」として断定しない
- 複数タブはWeb Locks APIと`storage.local`の期限付きロックを併用して排他する。
  ストレージ側は45秒で期限切れ、10秒ごとに更新し、所有者以外は進捗やロックを消さない
- 内訳では「未収集」と「取得失敗」を区別して表示するが、再取得対象としてはどちらも
  `needsCollect`で同じ扱いにする。月別表、`pendingTargets`、取得予定件数も同じ判定を使う

### 共有カードの画像

共有ボタンを押すと、文面と一緒に共有カード（既定1200x675のcanvas）を出すパネルを開く。
組み立てと描画は `share.js`。背景には手持ちの画像かテンプレートを使う。

- **𝕏の投稿画面（intent）には画像を添付できない。** URLで渡せるのは文面だけなので、
  画像は保存かコピーをしてもらい、本人に貼ってもらう。**この手順を画面に必ず書くこと。**
  黙って画像を出すと、投稿すれば付いてくると思わせてしまう
- カードは**文面と同じ集計値**から組む（`buildTotalShareCard` / `buildRankingShareCard` /
  `buildSummaryShareCard`）。カードのために集計し直すと、本文と画像で違う数字が出る
- **断り書きは画像にも載せる。** 画像だけが転載されることがあり、本文の断りは付いていかない
- 背景画像は**縦横比を保って全面を覆い**（`drawCover`）、上から暗く敷いて白文字にする。
  引き伸ばすと絵が歪み、敷かないと明るい画像で文字が消える
- 背景画像はcoverを100%として100〜300%まで拡大でき、canvasのプレビューを直接ドラッグして
  映す位置を調整できる。位置は縦横それぞれ-1〜1で持ち、縦横比を変えても相対位置を保つ。
  別画像を選ぶか「元に戻す」を押したときだけ、拡大率と位置を初期値へ戻す
- canvasには方向キーでの位置調整も用意し、画像が無いときはスライダーを無効化して
  ドラッグできるように見せない
- 選ばれた背景は**タブの中だけで持ち、ストレージへ入れない。** 画像1枚で
  収集済みデータを圧迫しかねない
- 収まらないショップ名は `fitText` で切って「…」を付ける。はみ出すと金額に重なる
- 順位表の金額・購入数は補足（`muted`）ではなく `value` の色で描く。作者名が太字なので、
  同じ薄さだと数字だけが読み取りにくい。**太さを変えたら測るときの字体も合わせること**
  （細い字で測ると、太くした分だけ名前に重なる）
- パネルは「テンプレート → 背景画像 → 文面」の順に置く。手持ちの画像を選ぶ欄が先に
  あると、画像を用意しないと作れないように見える。背景画像の枠と文面の枠は、
  どちらが高くても下端をそろえる（両方を伸ばす）
- **金額と点数は切ってはいけない。**「¥184,3…」では額そのものが変わるので、
  収まらないときは `fitFontSize` で字を小さくする
- 縦横比は `SHARE_RATIOS` から選ぶ（16:9 / 1:1 / 4:3 / 3:4）。描画は canvas の
  大きさから寸法を出すので、比率を足すときはここだけを増やせばよい。
  正方形や縦長では数字が横に潰れるため、幅が足りなければ2列に折り返す
- 画像の保存は `downloadBlob`。`downloads` 権限を足さない
- 画像の「コピー」と「保存」は投稿準備の主要操作なので、文面操作より目立つ同格のボタンとして並べる
- **縦横比ごとに組み方（`SHARE_CARD_LAYOUTS`）を持つ。余白だけ変えないこと。**
  文字の大きさも数字の並びもそのままで高さだけ伸ばすと、中身が上に固まって間延びする。
  縦長・正方形は数字を2列に折り返し、余った高さを段の間へ配る（`spread`）
- 背景のテンプレートは**その場でcanvasへ描く**（`shareTemplate(colorId, patternId)`）。
  外部の画像を読み込まない。見本のボタンも同じ描画関数で描く
  （色見本を別に持つと、実物と食い違っても気付けない）
- **色（`SHARE_TEMPLATE_COLORS`）と模様（`SHARE_TEMPLATE_PATTERNS`）は別々に選び、
  組み合わせが背景になる。** 色は**色相だけ**を持ち、彩度・明度は `TEMPLATE_HSV` に
  1か所だけ置く（`hsvColor`）。色ごとに描き分けると、同じ模様でも色によって
  太さや間隔が食い違い、選び直したときに別の模様に見える。色を足すときは色相を1行足す
- どちらも常に1つ選ばれている状態にする。「選択なし」を作っても下地の見た目が
  1種類増えるだけで、押し直して戻す操作を覚えてもらう必要が出る
- **模様は canvas の中心を原点にして敷く**（`patternDots` ほか）。端から順に敷くと
  幅や高さで割り切れないぶんが片側に余り、16:9では右へ寄って見える。市松は中心に
  格子の交点を置けば `i+j` の偶奇が変わらないのでそのまま点対称、波は位相を中心から
  測る（sinが奇関数なので上下の段が対応する）。**折れ線は右端を必ず打つ**。
  刻み幅で幅が割り切れないと右だけ線が途切れる
- フレークだけは散らばりが持ち味なので点対称にしない。位置は式で決める。
  `Math.random` を使うと描き直すたびに柄が変わる
- **見本のボタンは模様の間隔だけを詰める**（`SHARE_PREVIEW_STEP`、実寸は `patternStep`）。
  96x54の見本へ実寸と同じ間隔で描くと模様が1つ2つしか入らず、何の模様か見て分からない。
  描画関数そのものは実物と共通のまま変えないこと
- 優先順位は「アップロードした画像 > テンプレート > 既定の下地」。
  画像を選んでいる間はテンプレートが効かないので、見た目でもそれを示す
- **パネルを挟むことで、共有を押してから投稿画面を開くまでが1クリックになった。**
  収集を挟むと`window.open`が止められることがあったが、パネル内のボタンは
  そのままクリック操作なので止められない

## 6. 調査済みの技術知見

### 集計中のCSPエラーは仕様

```text
Loading the script 'https://www.google.com/recaptcha/enterprise.js?...'
violates ... "script-src 'self'"
```

原因はBOOTHのレスポンスヘッダ`Link: <...enterprise.js>; rel=preload; as=script`です。
ブラウザがHTMLを見る前に先読みを試み、拡張のCSPがブロックします。通信は発生せず、集計にも影響しません。
fetch側から抑止できず、CSPへgoogle.comを追加するとMV3のリモートコード禁止に抵触するため修正しません。

HTMLからタグを除去する対応は、ヘッダ起点のエラーには無効で、必要なHTMLまで削る危険だけが残るため撤去済みです。
`dashboard.js`の`fetchDoc`付近とREADMEにも経緯があります。

### DOMParser文書はサブリソースを取得しない

DOMParserで生成した文書について、script、link（preload、modulepreload、prefetch、stylesheet）、
img、iframeの7種類すべてで通信が発生しないことを、開発環境とユーザーのChromeで実測済みです。
無駄な通信を防ぐ目的でタグ除去を追加しないでください。

### ギフト金額の取得

ギフトは支払明細の項目ではなく、ショップ内の商品グループの見出しです。

```html
<div class="sheet-group">
  <b class="u-tpg-title3">ダウンロード商品</b> ... 商品6件 各¥425 ...
</div>
<div class="sheet-group">
  <b class="u-tpg-title3">ギフト</b>          ... 商品6件 各¥425 ...
</div>
```

`.sheet-group`のうち見出しが「ギフト」のものを探し、その配下の`.u-tpg-caption1`の金額を合計します。
BOOSTは`BOOST¥ 0`のようにラベルと金額が同じ要素に入るため、文字列中の`¥ 金額`を拾う
`parseYenAmount`を使います。グループ自体がなければ0と断定せず`null`（不明）にします。

実データで、お支払金額¥5,100、ギフト¥2,550となり、全グループ小計の合計が支払金額と一致することを確認済みです。
